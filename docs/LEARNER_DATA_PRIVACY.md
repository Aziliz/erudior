# Privacy-preserving learner data architecture

## Boundaries and original scope

This engine implements local anonymous practice, opt-in server-backed account progress, isolation from the credential registry, retention/deletion controls and recovery. It does not create public website accounts. All production learner identity/trust/database configuration is absent; the production service denies access before touching a database. The application retains local practice by default and never uploads in the background.

The two outstanding review obligations are not implemented by this feature: content review was skipped at the user's request, and independent course/accessibility review with real learner pilots remains pending. No synthetic test is called a real learner pilot. Existing courses are unchanged; adoption of engines into courses is a subsequent task.

## Minimal, explicit checkpoints

Use **Family/Classroom → Learner privacy** for a current local family profile after unlocking the adult area. Without a family, **Courses → Study tools, skill evidence, and data → Local practice privacy and recovery** offers anonymous local portability. Every operation rechecks the current local scope; local password/membership/deletion changes invalidate prior access. This is local device authorization, not verified institutional identity or parental consent.

Select the courses to include and supply a recovery passphrase of at least 12 characters. The passphrase stays in memory and is not stored with the checkpoint, sent to the service, or recoverable from an identity grant. AES-256-GCM uses a fresh 16-byte salt and 12-byte IV with PBKDF2-SHA-256 (600,000 iterations). Authenticated additional data binds the format/schema and pseudonymous namespace/account/profile. Save the passphrase separately: losing it makes encrypted checkpoints unreadable.

The strict plaintext allowlist contains exact installed course digest/revision, non-quiz-gated reading/practice lesson completion dates and aggregate numeric practice counts. Course titles are displayed locally, not copied into the payload. No family names, birth dates, password/PIN/recovery hashes, classroom secrets, notes, writing, audio, photos, graded attempts, module passes, human reviews, placements, instructional credit or credentials are included. Practice counts remain portable observations; recovery never reinserts them into scored attempts or drills. Encrypted data and pseudonymous metadata can still be personal data; encryption is not anonymization. Course identifiers, sizes, timestamps and access metadata remain observable to the service.

Encrypted portable files may be intentionally recovered into another selected local profile. The staged preview discloses the source pseudonymous scope; it is not identity proof. Wrong passphrases, changed/missing sources, malformed data, quiz-gated checkpoints and stale local progress are rejected. Explicit application adds missing plain lesson checkpoints only, preserving existing dates and all other progress. This can change local reading-completion/date displays, but does not grant grades, assessment passes, approved hours or qualifications. Full encrypted family backups remain a separate richer local-only recovery mechanism.

## Optional account progress and conflict handling

The app integration point accepts a separately configured external identity provider. It does not accept a community author cookie, local typed name, imported public key or course/credential signing key. Short-lived Ed25519 grants bind issuer, purpose, audience, namespace, opaque account/profile, adult-self or verified-guardian authority, consent receipt/version and read/write/erase scopes. The trusted issuer must verify the real relationship/consent and withdrawals before issuing each grant; the local checkbox is only explicit upload intent, not legal consent verification.

After authorized configuration, explicitly opt in, prepare a newly account-bound checkpoint, inspect it, queue it and send it. Only ciphertext and bounded metadata leave the device. Queue contents persist encrypted for manual retry after interruption/offline; no passphrase or grant is persisted. Request IDs and exact digests make lost-response retries idempotent. Revision CAS rejects competing writes. A conflict never silently merges or overwrites: explicitly discard the local queued transfer, retrieve the current remote revision, inspect/decrypt it, then deliberately prepare a replacement if desired. Retrieving does not apply local recovery automatically.

HTTP uses fixed HTTPS origin, no cookies, no redirects, no referrer and no cache. Identifiers/grants are not placed in URL paths/query strings. The production app does not configure this adapter or initiate identity enrollment.

## Retention, deletion and recovery

Remote retention is explicit, 1–30 days per write. Expiration denies reads and redacts ciphertext/retry receipts. The reusable sweep function supports proactive deletion of expired rows; production must arrange monitored sweep execution, including inactive profiles. Terminal hashed-subject tombstones reject stale grants, offline queues and imported snapshots. They are retained to prevent resurrection and remain linkable pseudonymous metadata; actual operational retention policy and any separately authorized re-enrollment require review.

### Anonymous local inventory, erasure and recovery

Without a local family workspace, the privacy workspace offers a count-only inventory of anonymous learning records and the unfinished session. The separate **encrypted anonymous archive** preserves full local progress, validated historical submissions, the session and available work/log attachments; it is not the minimized cloud checkpoint and is never uploaded. Missing attachment bytes are explicitly listed. The archive contains source digests rather than course/bank content, has a bounded size, and uses the existing AES-GCM/PBKDF2-600000 recovery envelope. Keep the passphrase privately; loss cannot be repaired by the server.

Erasure requires a fresh inventory, a typed confirmation and acknowledgement that an archive was saved or deliberately declined. It removes only anonymous progress/session and safely unreferenced work/log attachment blobs. Installed courses/banks, family profiles, authentication, theme and installation bookkeeping are preserved. Shared or uncertain attachment references are retained and reported, not falsely described as erased. Replacement also clears only the anonymous local transfer association and encrypted queue; changes to that state invalidate an earlier inventory. Saved/exported files, separate browser downloads and remote checkpoints remain separate deletion responsibilities. **Courses → Study tools, skill evidence, and data → Reset attempts** still removes question history/statistics only; it is not this scoped erasure operation.

The backend compares the exact inventory state before replacement and advances an anonymous generation. Old tabs/timers cannot resurrect cleared progress or session data; reload the application after confirmed erasure/recovery before saving new practice. Browser IndexedDB replacement coordinates tabs atomically. Native coordination covers webviews in one app process, not independently running app processes; do not run concurrent native instances during cleanup. Native multi-file replacement is not power-loss atomic: an abrupt crash during recovery can leave newly inserted attachment bytes or make the pending session unavailable before progress commits. Retain the exported archive, restart, re-inventory and retry deliberately. Ordinary write errors attempt rollback of newly inserted files/session; cleanup failures explicitly report possible retained bytes.

Recovery decrypts locally into a staged preview and requires explicit replacement confirmation. A newer local change invalidates the preview rather than being overwritten silently. Historical learner results remain snapshots; imported adult competency decisions are marked unverified, cross-profile credited-hour links are removed from the operational projection, and no consent/server association/credential authority is restored. An archived unfinished session is activated only when structurally valid and bound to the exact installed question bank; a recovered-session-only digest is rechecked at actual resume and retained on subsequent session saves. Otherwise it remains in the archive without resuming. This content-match marker is not authentication of imported answers or proctoring. Course source changes are disclosed, not repaired by replacing installed courses.

Authenticated remote erasure is distinct from forgetting a local association or deleting a local learner. Erase remotely while online/authorized, then inspect the response. Local forgetting clears consent/binding/queued ciphertext only; it does not promise remote erasure. Local full-profile deletion removes association data and preserves a deletion marker that rejects stale local writers. Encrypted family restore always strips all cloud opt-in, bindings and pending transfers, while preserving the union of current and imported local tombstones. A restored file cannot activate server authority. Existing immutable evidence backup/quarantine behavior is unchanged.

The server stores one current encrypted checkpoint plus bounded retry metadata (at most 10,000 write receipts per active slot), not historical plaintext records. At that ceiling new writes fail closed; read/export and terminal erase remain available. Client keys are never uploaded. Database encryption at rest, backup access controls and deletion across operational backups require separately authorized production operations. A complete database rollback can omit a later tombstone; self-contained data cannot detect that omission. Production recovery must reconcile trusted monotonic deletion records before enabling reads/writes. There is no arbitrary server restore endpoint. Credential registry bindings, issuer trust and records are separate and untouched.

## Deployment prerequisites and verification

Before any real deployment: separately authorize the app identity/guardian-consent provider and public-key trust, isolated learner database/migration, exact app origin, grant withdrawal process, monitored retention sweep, deletion/backup reconciliation, access-log minimization, incident/recovery procedures and applicable policy/legal review. No compliance, identity-verification or certification claim is made by this code. No real learner records, persistent auth credentials, trust registration or security settings were created during development.

Tests cover strict minimization and crypto boundaries, wrong keys/passphrases/purpose/audience/scopes, fresh actual-App authorization, source drift, immutable historical preservation, offline/lost-response retry, CAS conflicts, explicit discard, terminal expiry/erasure, encrypted backup consent stripping and privacy deletion. A synthetic isolated D1 and certificate-verified HTTPS harness exercises actual worker routing/SQL; a browser harness uses synthetic ephemeral grants and real client encryption/store logic. These are engineering verification, not real learner pilots or production consent verification. Existing signed course release, licensing, credential isolation and all earlier engine pipelines remain required and unchanged.
